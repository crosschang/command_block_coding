## 현재 근거와 한계

2026-11-15 20-22-39 영상(17.75초)에서 게임 화면 복귀 약4.2초, BENCH_READY/BENCH_SKIP 약15.5초를 확인했다. 모드0, defs9, CAPTURE9/9, CHECK168/168, STORE9/9, DIAG9/9, CHAT20/20, OUTPUT10/10, 생략0으로 정상 완료다. 화면 복귀 기준 약11~12초이며 전체 측정 구간이 순수 계산 시간이라는 뜻은 아니다. 영상에는 사용자 소스와 여러 비교 실행이 보이지 않아 반복문 원인 확정은 불가하다.

앞선 블록 전환 실행은 defs0으로 끝났다. 기존 TS→Blocks 변환 결과에서 독립된 FunctionFile 정의9개와 on-start 안의 연속된 begin/finish가 확인됐다. 문법적 블록 변환 성공만으로 측정 순서 보존을 보장하지 못했다. 기존 자료를 삭제하지 않으며 이번 전용 시험으로 순서 문제를 피한다.

## 적용

master 확장을 업데이트한 뒤 tests/dev/STARTUP_SCALE_MAIN.ts로 **사용자** JavaScript 전체를 교체한다. Extension main.ts에 덮어쓰지 않는다. 코드의 StartupProbe.scale(1) 숫자만 바꿔 매번 새로 실행한다. 한 프로그램 실행 중 시험을 연달아 호출하면 SCALE_RESTART_REQUIRED로 차단해 등록/캐시 상태 혼합을 막는다.

이 API는 StartupProbe의 고급 STARTUP TEST 블록이다. 새 파일은 tests/dev의 사용자 프로그램과 Node 검사 파일, 이 문서다. 런타임 API는 기존 pxt.json.files에 들어 있는 function_file.ts에 추가하므로 files 변경은 없다. pxt.json.version 0.0.19는 바꾸지 않는다. 행동팩 변경·교체나 scoreboard 목표 생성은 필요 없다.

전용 단일 시험 블록 내부에서 begin → 정의/검사/등록 → snapshot → 최종 player.say를 순서대로 처리한다. 사용자 프로그램에는 별도 FunctionFile topblock이나 begin/finish가 없다. PXT 변환 결과에서 on-start 아래 startup_probe_scale 하나만 생성되어 기존 순서 분리 원인을 제거한다. 실제 Education 블록 왕복/실행은 실게임 검증 대상이다.

## 시험 번호

기존 StartupProbe.begin의 모드0~5와 **다른 시험 번호**다. 특히 이번3번은 기존 출력 제거 모드3이 아니라 **1함수256명령**이다.

| 번호 | 함수 수 | 전체 명령 수 | 실제 채팅 등록 호출 | 비교 |
|---|---:|---:|---:|---|
| 1 | 1 | 8 | 4 | 1·2·3 명령 수 |
| 2 | 1 | 64 | 4 | 공통 기준 |
| 3 | 1 | 256 | 4 | 1·2·3 명령 수 |
| 4 | 8 | 64 | 18 | 2·4·5 함수 수 |
| 5 | 32 | 64 | 66 | 2·4·5 함수 수 |
| 6 | 1 | 64 | 0 | 2 ↔ 6 |
| 7 | 8 | 64 | 0 | 4 ↔ 7 |
| 8 | 32 | 64 | 0 | 5 ↔ 8 |

각 함수 본문은 같은 공개 Command AST adapter로 scoreboard players add #r cbx_scale 1을 캡처한다. 명령 수를 모든 함수에 균등 배분한다. 2/6,4/7,5/8 쌍은 정의 이름/순서/컴파일 명령까지 같고 채팅 등록만 다르다. 수집·Compiler·Validator·내부 저장·진단/INFO 저장은 전부 유지한다. 시험 생성 내부에는 같은 형태의 for가 사용된다. 이는 사용자 반복문 유무를 비교하는 시험이 아니며 기존 개별64블록 시험을 대체하는 for 성능 증거가 아니다.

모든 시험에서 함수별 안내 출력은 공통 생략해 출력 수 차이를 통제한다. 출력 제거를 제품 해결책으로 채택했다는 뜻이 아니다. 원래 일반 실행 동작과 기존 모드의 의미는 바꾸지 않는다. 프로파일링은 기본 OFF이며 이 블록을 호출한 실행에서만 활성화된다.

실제 세계 명령 실행은 모든 경우 차단한다. native player.execute, GameTime 쿼리, 추가 pause, heartbeat, Worker를 추가하지 않는다. 최종 SCALE_RESULT 한 번만 player.say한다. 이 출력 자체의 전달 대기는 영상 시간에 포함된다. 체크 값은 시간 아닌 반환/진입 호출 수다. CHAT OFF에서도 래퍼 계수 CHAT=n/n은 증가하므로 SKIP CHAT=n을 함께 읽어야 한다.

## 한 영상으로 녹화

1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 순서로, 숫자만 바꾸고 매번 새 실행한다. MakeCode 닫힘부터 SCALE_RESULT가 보일 때까지 촬영하고 결과 후3초 유지한다. 가능하면 마지막에2를 한 번 더 반복해 예열/실행 순서 영향을 살핀다. 시작 안내 출력을 추가하지 않는다.

60초 동안 결과가 없으면 그 사례는 '60초 내 완료 미확인'으로 남기고 C로 다음 번호로 바꾼다. C로 돌아간 뒤 늦게 뜬 결과를 다음 사례의 완료로 혼동하지 않는다. case=번호를 확인한다. 채팅 등록을 제외하는6·7·8에서는 ? 진단도 등록되지 않으므로 입력할 필요가 없다. 무응답만으로 계산 실패/영구 정지를 단정하지 않는다.

단일 순서 한 번의 차이는 예열 등과 섞일 수 있다. 차이가 큰 쌍은 순서를 뒤집어 재확인한 뒤 구조 변경 여부를 판단한다. 2·4·5 증가와 6·7·8 증가를 함께 보아 함수별 검사/캐시 비용과 채팅 요청/응답/재개 비용을 구분한다. 게임 내부 등록 처리와 MakeCode 실행 재개 중 어디가 느린지는 이 시험만으로 확정할 수 없다.
