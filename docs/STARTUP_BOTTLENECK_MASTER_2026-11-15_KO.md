# 시작 병목 제외 비교 시험 — master 통합·기본 OFF

## 통합 기준

사용자의 MakeCode 직접 연결 편의를 위해 계측 기능을 master로 통합했다. 별도 개발 브랜치로 전환할 필요가 없다. 실제 pxt.json은 0.0.17이며 버전/파일 등록을 변경하지 않았다.

일반 프로그램에서 StartupProbe.begin()을 호출하지 않으면 모든 제외 기능은 OFF다. 현재 master의 정상 정의 자동 출력 억제·INFO/경고 저장·상세 조회·오류 차단·수동 PREVIEW READY·분할 송수신을 보존한다.

전용 시험 코드가 begin(0..5)을 호출할 때만 제외 비교 기능을 켜고 실제 FunctionFile 실행을 차단한다. 시험 중 mode0은 이전 출력 제거 수정 전 edcb16c5072a2352eb6a64a9f70aa98cc350478d의 자동 INFO/OK와 정의 중 READY 가이드 동작을 재현한다. 따라서 이전 변경을 원인 판정에 섞지 않는다. 이 재현 경로는 정상 사용에서는 실행되지 않는다.

전용 시험 후 실제 실행으로 돌아갈 때는 일반 사용자 프로그램으로 교체해 새로 실행한다. 한 번 켠 프로브가 실행 도중 자동으로 일반 모드로 바뀌지 않는다. 행동팩은 수정/교체할 필요 없으며 소스도 저장소에 추가하지 않는다.

## 측정 방법과 한계

이 시험은 단계별 밀리초를 측정하지 않는다. 확인한 Minecraft 공개 배포 번들의 core 선언에서는 게임 호출 없이 사용하는 시간 API를 확인하지 못했으므로 control.millis/Date.now 같은 미확인 API를 만들지 않았다. 참고 자료는 https://minecraft.makecode.com/ 에서 연결된 공식 target.js 배포 번들이다. 공개 번들과 사용자의 Education 내장 런타임이 완전히 동일하다고 가정하지 않는다.

대신 같은 아홉 FunctionFile/명령 구성에서 한 단계씩 제외하고, 녹화에서 공통 게임 복귀 지점부터 BENCH_READY가 처음 나타나는 시점까지 비교한다. 숫자는 UNIT=CALLS, 즉 시작/반환 호출 횟수다. 시간으로 읽으면 안 된다. `CHECK=168/168`은 검사 함수 진입/반환 호출 수이며 168ms도 168명령도 아니다.

아래 제외 비교로 빨라져도 한 번만으로 원인이 확정되지는 않는다. player.onChat의 후속 효과, 출력 자체의 지연, 실행 순서/예열/스케줄링이 함께 달라질 수 있다. 완료 마커는 모든 정의 처리가 반환된 뒤 보내지만 그 마커 전송 시간도 영상에 섞인다. 총시간 차이는 해당 구간의 단독 내부 실행 시간이 아니다.

## 여섯 모드

시험 파일의 `StartupProbe.begin(0)`에서 숫자만 바꾼다. 매 모드는 프로그램을 새로 실행한다. 실행 중 모드 전환은 하지 않는다.

| 모드 | 제외하는 작업 | 비교 대상 |
| --- | --- | --- |
| 0 | 없음. 원래 검사·저장·진단·채팅 등록·안내 출력 수행 | 기준 |
| 1 | player.onChat의 실제 이벤트 등록 | 0과 비교: 채팅 등록 및 그 후속 영향 |
| 2 | 내부 함수/명령 배열 저장 | 0과 비교: 내부 저장 |
| 3 | 정의별 정상 안내/프리뷰 가이드 출력 | 0과 비교: 출력. 이전 수정 적용본이 아니라 통제된 제외 비교 |
| 4 | 진단 저장·표시 캐시 정리와 채팅 등록 | 1과 비교: 채팅 등록을 양쪽에서 제외한 상태의 진단 정리 |
| 5 | Core/Preview 검사와 진단 정리·채팅 등록 | 4와 비교: 진단·채팅을 양쪽에서 제외한 상태의 검사 |

진단 요약 갱신에는 페이지 채팅 등록이 함께 들어 있어 모드4에서 채팅까지 양쪽 비교군과 맞춰 제외했다. 모드5의 검사에는 Core Validator와 Preview compatibility 검사가 포함되며, 검사 결과 중복 정리 비용 일부도 달라질 수 있다. AST/블록 값 생성 자체는 모든 모드에서 유지한다.

모드4/5의 진단 생략, 모드5의 검사 생략은 실험 동작이다. 통과/정상/안전 판정으로 사용하면 안 된다. 모드0/1/2/3에서는 INFO/경고 데이터가 유지된다. 모든 모드에서 작성한 FunctionFile의 실제 실행을 차단한다.

## 적용

1. 기존 프로젝트를 보존하고 별도 MakeCode 시험 프로젝트를 사용한다.
2. 기존 `https://github.com/crosschang/command_block_coding` 확장을 최신 master 변경으로 업데이트한다. 브랜치 주소를 바꿀 필요가 없다.
3. tests/dev/STARTUP_BOTTLENECK_MAIN.ts 전체를 사용자 JavaScript에 적용한다. 이 파일을 Extension main.ts에 덮어쓰지 않는다.
4. mode=0으로 시작한다. 실제 함수 명령은 실행하지 않으므로 목표 생성·팩 재설치는 필요 없다. 기존 팩 활성화 상태는 비교 내내 동일하게 유지한다.
5. ▶ 실행 직전부터 녹화하고 게임으로 돌아온다. C를 다시 열거나 채팅을 반복 입력하지 않는다.
6. BENCH_READY와 BENCH_SKIP가 나올 때까지의 영상을 보존한다. 무응답이면 그 자체를 기록한다.
7. 같은 코드를 mode=1로 바꿔 새로 실행하고 비교한다. 첫 권장 순서는 0→1→0이다.
8. 등록 영향이 작거나 구분이 안 되면 1→4→1, 4→5→4를 이어 검사/진단 후보를 확인한다. 저장·출력은 0→2→0, 0→3→0으로 비교한다.

월드 재입장으로 빨라진 결과를 동일 시험의 해결로 기록하지 않는다. 영상을 비교할 때 앞선 실행의 남은 안내와 현재 BENCH mode 번호를 구분한다. 실행 시간과 입력 사이의 대기 시간을 섞지 않는다.

시험 전용 begin/finish 호출은 측정 설정이며 일반 블록 작성 흐름이 아니다. 별도 값 조회·브릿지 블록을 정식 도구상자에 추가하지 않는다. 실험이 끝나면 확장은 그대로 두고 일반 사용자 시험본으로 교체해 새로 실행한다.

## 결과 읽기

예:

```text
BENCH_READY mode=0 defs=9 UNIT=CALLS CAPTURE=9/9 CHECK=168/168 STORE=9/9 DIAG=9/9 CHAT=20/20 OUTPUT=10/10
BENCH_SKIP mode=0 CAPTURE=0 CHECK=0 STORE=0 DIAG=0 CHAT=0 OUTPUT=0 EXECUTION_DISABLED
```

- READY: 정의 아홉 개의 처리 호출이 반환되었다. 게임 실행 PASS가 아니다.
- CAPTURE: 정의 본문의 블록/명령 생성·캡처 처리 호출 수.
- CHECK: Core/Preview 검사 호출 수. 중첩 execute에서 추가 호출이 포함된다.
- STORE: 내부 함수/명령 목록 등록 호출 수.
- DIAG: 정의 진단 교체/표시 캐시 갱신 호출 수.
- CHAT: 채팅 이벤트 등록 시도/반환 호출 수. 제외 모드에서는 실제 API를 호출하지 않아도 시도/반환을 센다.
- OUTPUT: 정의별 완료 안내와 READY 가이드 출력 처리 호출 수.
- SKIP: 각 구간이 의도적으로 제외된 횟수.

시작/반환 수가 다르면 완료되지 않은 호출이 있을 수 있으므로 영상과 함께 확인한다. 마커 자체가 나오지 않는 경우 이 코드만으로 어느 호출에서 멈췄는지 확정할 수 없다.
