# V1 호출 수 비교 실게임 결과

근거: 사용자 영상 `2026-11-11 22-03-07.mp4`, 약 96.82초.
TRANSPORT_PROBE_V1_MAKECODE_MAIN.ts의 QLAT 시작·준비·BEGIN/END 로그와 대조했다.
아래 수치는 OCR을 보조로 사용하고 영상 프레임에서 직접 확인했다.
Education/PXT 정확한 게임 빌드와 실제 로드된 Extension 커밋은 미확인이다.

## 계측 해석

TICKS는 GameTime 차이이며, 밀리초나 API 내부만의 소요 시간이 아니다.
시작·종료 timeQuery 호출과 MakeCode의 루프 처리도 포함한다.
N=0에도 같은 계측을 수행했다. 낮 시간이 멈춘 것과 GameTime 계측을 구분한다.

이번 영상에서는 N을 거의 두 배로 늘리면 계측값도 거의 두 배가 된다.
N=0은 0~1틱, N=128은 47~49틱이었다. 따라서 호출 수와 관계없이 고정으로
2~3초 기다린다는 설명보다, Boolean 확인 호출을 순서대로 실행하는 비용이 주요
원인 후보라는 설명을 지지한다. 실게임 대표 12회 관찰이며 Minecraft나 Script API
전체의 성능 상한을 증명한 것은 아니다.

## 영상 표시 간격

0.5초 간격 추출 프레임 163/164에서 RUN11 BEGIN은 81.00~81.50초 사이에
최초 표시됐다. 프레임 168/169에서 END는 83.50~84.00초 사이에 최초 표시됐다.
이 대표 128회 실행의 BEGIN→END 표시 간격은 약 2.0~3.0초다.
영상의 근사 표시 간격이며 49틱을 초로 환산해서 얻은 값이 아니다.
입력→BEGIN은 별도 구간이고, 다른 모든 RUN을 같은 정밀도로 시간 측정한 것은 아니다.

## V4와의 관계 및 다음 판정

V4의 142/161probe에서 READ_TICKS=48/55였던 기존 결과와 이번 128회 47~49틱은
비슷한 규모다. 명령 길이·디코더 처리·ACK·계측 범위가 다르므로 이번 호출당 비용을
모든 데이터에 그대로 적용하지 않는다.

이번 영상에는 qlatlocal·qlatwire·qlatstatus 실행이 포함되지 않았다.
따라서 직접 문자열 반환 후보의 실게임 성패는 미판정으로 유지한다.
추가 호출 수 실험을 늘리기 전에, 이미 제공한 같은 사용자 코드와 별도 실험팩으로
qlatlocal, qlatwire 1/2/3 및 각 qlatstatus를 확인한다.

수신이 가능하면 많은 비트 확인을 피할 가능성이 있지만, 토큰·소유자·오래된 응답·
변조·길이를 검증하기 전에 정식 경로를 교체하지 않는다. 후보가 작동하지 않아도
모든 수신 경로의 불가능으로 확대하지 않는다. 기존 V4를 보존하고 필요한 데이터만
조회·이미 받은 배열 재사용을 우선한다.
